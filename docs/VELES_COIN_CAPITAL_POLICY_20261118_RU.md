## Смысл поля — маржа, а не номинал сделки

До изменения размер VELES рассчитывался как
`deposit * allocation_pct / 100` **на каждую секцию**.
У пользователя было два требования: доля депозита на конкретную
монету и фиксированный USDT-объём на монету. Важно, что
у одной монеты может быть несколько секций/диапазонов.

Новый единый `allocation_mode`:

| Значение | Интерпретация | Совместимость |
|---|---|---|
| `section_pct` | `allocation_pct` процентов депозита на отдельную секцию | Старый режим по умолчанию; не меняет имеющиеся сетки |
| `coin_pct` | `allocation_pct` процентов депозита — **общий бюджет маржи на монету**, все секции делят его | Новый явный режим |
| `coin_fixed` | `allocation_fixed_usdt` — **общий бюджет маржи на монету в USDT**, все секции делят его | Новый явный режим |

Суммы — **первоначальная/плановая маржа**, а не плечевой номинал.
Номинал = плановая маржа × плечо. Комиссии, наличие свободных
средств, ограничения Bybit, свежесть mark-price и защита ликвидации
по-прежнему проверяются другими независимыми компонентами.

## Единый механизм

- `bcc/coin_allocation.py`: чистая функция вычисления целевой маржи
  и уже зарезервированного объёма на монету. Для каждой открытой
  позиции берётся консервативный максимум из текущей/будущей маржи
  и **полного плана сетки** (`budget / leverage`). Для ожидающих
  сеток учитывается их предзарезервированная маржа. Нельзя считать
  невыставленные DCA-ордера свободным капиталом.
- `bcc/strategies.py`: на входе для всех секций применяется
  остаток общей квоты монеты. Если квота исчерпана/непрочитаема,
  запись диагностирует причину блокировки без открытия сделки.
- `bcc/trading.py`: низкоуровневый `enter()` снова проверяет
  лимит до изменения PAPER-счёта. Прямой вызов без подтверждённой
  квоты отклоняется. В фиксированном режиме нельзя увеличить квоту
  переданным внешним значением. Переход уже зарезервированной
  ожидающей сетки в открытую позицию **не расходует квоту повторно**.
- Не добавлен второй счётчик/SQLite-бюджет. Вся оценка происходит
  по авторитетной книге позиций в той же транзакции.

## Настройки и наследование

- `bcc/config.py`: старый JSON без новых полей нормализуется в
  `section_pct`. Новые поля валидируются; неизвестные режимы,
  NaN/Infinity, некорректная сумма не допускаются.
- Общие настройки → индивидуальные по монете → настройки секции
  продолжают поддерживаться. Для `coin_pct`/`coin_fixed` все
  секции одной монеты обязаны использовать **одну активную квоту**;
  конфликт в какой-либо секции блокирует сохранение с пояснением.
- Polymarket, GRID и Pump&Dump имеют отдельные собственные правила
  размера ставки; их нельзя обмануть скрытой JSON-настройкой маржи VELES.
- `bcc/widgets.py` и `bcc/wizard.py`: настоящий Modern Qt выбор
  режима, процента и фиксированной суммы; неактивное поле
  заблокировано в редакторе, но сохраняется без потери значения.
- `bcc/constructor_review.py` и `bcc/wizard_presentation.py`:
  аудит изменений, сетка и сводка используют **тот же расчёт**;
  явно указывается, что общий лимит делится между диапазонами.
- Изменение политики не закрывает открытые позиции и не изменяет
  сохранённый баланс. Если новая квота меньше занятых средств,
  новые входы будут заблокированы до освобождения капитала;
  существующие DCA и выходы не должны останавливаться.

## Незакрытые release-gates

1. На независимом чистом checkout компиляция/тесты новых модулей
   и **вся** исходная Linux/Windows регрессия; ошибки — общий пакет
   архитектурных исправлений, не отдельные заплатки.
2. Native Windows Modern Qt E2E: GUI изменение общего и индивидуального
   лимита, Stop/Restart с сохранёнными позициями и pending,
   удаление/импорт/экспорт, документация владельцев блокирующих лимитов.
3. Отдельная реальная Bybit WS/mark/funding PAPER acceptance с
   собственным Hub и публичным независимым временем. Ни одна
   не подменяется моками этой новой политики.
4. Полный source sealing новой чистой папки, независимый review,
   отсутствие вмешательства в работающие Windows-боты; затем
   окончательная приёмка и только после неё релиз.
