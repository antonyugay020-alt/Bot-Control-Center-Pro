# Live history handoff — NOT RELEASE

Baseline `c01a8951411438d5dcb4283eb5a4ebb13203d729`. The two provided live Windows PAPER snapshots report the same running worker, 831 configured instruments, 19 and 33 positions, 22 and 63 ledger-audited fills, and respectively three and 13 unavailable history channels. The later snapshot reports one unavailable quote channel and records both quote and history recovery events. New PAPER entries occurred between the snapshots without a worker restart. These snapshots are not atomic and do not prove the remaining history timeouts have a common cause or that every instrument recovered. Windows automated QA for this baseline reported 3979 tests, zero failures and errors, five skips; the manual Qt acceptance result for this session has not been received.

An independent negative regression exposed a separate safety defect: successful scheduler history could be cached and replayed alongside later position quotes after its original last exchange candle had aged beyond the 120-second source validity limit. Direct tests with 121- and 240-second-old candles reached a deliberately forbidden strategy on the baseline. The Windows reports do not establish that an actual trade used stale history; this is a separately reproduced defect.

Scheduler-originated history now carries a live-history marker through normal fetches, cached position history and handoff retries. The financial owner rechecks the original last candle timestamp against the existing `PublicData.candles` rule immediately before strategy evaluation. Stale, future or malformed timestamps remove the history from the decision and cause an explicit stale-history diagnostic; they are never retimestamped. A fresh executable book still reaches the existing protective-exit path. A stale scanner history is placed on the existing bounded fair retry lane for a new fetch and a new strategy evaluation, not replayed as an old order or signal. Tests cover expired and malformed timestamps, future candles, repeated cached quote handoffs, protective exits, fresh refetch, prioritisation, admission and ledger integrity. This is not a claim that the Windows Hub history timeouts themselves are resolved.

A second regression demonstrated that a candle fresh at entry to `process_tick` can expire while the account transaction is being acquired and validated. The owner now rechecks the same original timestamp again at the actual strategy boundary and uses that refreshed decision time; an aged candle still triggers bounded refetch rather than reuse. This does not relax the independent `PaperExecutor` book-freshness check. The earlier incomplete load and regression runs before this second check are not final verification.

The existing subprocess lifecycle fixture formerly supplied historical candles older than the public-data validity window; the new owner guard correctly exposed this in full regression. Its isolated replay now advances its own synthetic market clock with valid closed candles and explicitly advances the clock before the exit candle, preserving bar-close entry and exit tests without changing the operating-system clock. All seven real-worker subprocess tests pass in Linux with this fixture. These simulations are not Windows acceptance or live exchange evidence.
