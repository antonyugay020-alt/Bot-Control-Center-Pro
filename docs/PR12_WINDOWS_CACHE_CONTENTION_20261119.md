# Windows PAPER recovery investigation — NOT RELEASE

Baseline `886293737894a43d58935959f4b2a983909ea05a`. The supplied native Windows automated QA receipt reports 3965 tests, zero failures or errors, five skips and matching source integrity. The manual QA record marks all 36 scenarios `NOT_RUN`; it is not acceptance. Three late snapshots were taken after the isolated QA worker had stopped, and cannot establish live market recovery. They show 117 ledger-audited PAPER fills, all with book-age evidence; the last new position in that ledger was recorded at 14:13:34 local time, while later DCA and manual exits occurred. A prior live snapshot at 14:22 reported a stale priority position, paused entry, eight history errors and quote errors. Connected WS transports do not establish that every held symbol is fresh. The account report combines non-atomic captures and cannot by itself establish the exact source or duration of every error.

The worker log separately records 322 local read-contention timeouts, growing state and tick duration up to 4575 ms. In an isolated copy of the supplied SQLite snapshot, a no-op ledger transaction took approximately 127–174 ms on Linux, and profiling showed repeated validation, parsing and serialization of the accumulated document. These are independent observations, not proof that this operation alone caused the Windows stall. Cache reader contention is independently reproducible: at baseline `test_slow_scanner_reader_does_not_block_portfolio_reader` failed with `CacheContention` while another WAL read transaction was open.

The implementation uses a bounded pool of four independent read-only WAL connections. Each read holds a distinct guarded connection, retains a consistent read snapshot and performs the same committed provider-denial checks. Saturation is still bounded and remains a contention error, not permission to use stale data or bypass a denial. Readers and the writer are explicitly closed; no user account or live service is touched by the test. Regression coverage checks concurrent reads, provider-denial fencing, query-only behavior, closure and reuse of any freed pool slot. This addresses one reproduced cause, not all observed Windows delay. Full source-matched regression, integrated load, real recovery and native Windows Qt E2E remain mandatory.

For manifest `8e21520af0367dea8feaedd6a0829a8b865b215f90cb8fa7891a06c1dd24121a`, the partitioned Linux regression ran 3967 tests with no failures, errors or skips. The standalone public Bybit WS/Hub/client probe passed 24 rounds across ten symbols; the isolated Hub was retired. The 824-symbol synthetic WS/Hub/scheduler/worker/SQLite scenario completed the initial scan in 367.8 seconds and eventually admitted a new PAPER position after simulated disconnect, HTTP fences and fresh data; the harness advanced the risk retry deadline, so this does not establish recovery at the unmodified retry time. Logs and regression receipts are under `docs/evidence/pr12_20261119_readpool/`. Only evidence and this note were added after these executions; application and test code were unchanged. The root cause of the long Windows cycle and actual 824-symbol recovery remain open.
