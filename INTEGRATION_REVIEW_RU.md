## Системная идентификация процессов

PID в Popen/сохранённом состоянии относится к пространству вызывающего процесса.
Хостовый /proc может использовать другой PID. Все контуры Lifecycle, launch
claim, Hub, Runtime health, guardian и QA-cleanup обращаются к одному process_os.
На Windows и обычном Linux провайдер использует psutil без перевода PID. При
различающихся пространствах Linux чтение подтверждается NSpid и inode точного
PID namespace. Кэш — только подсказка: каждое использование проверяется заново.
Отсутствие процесса подтверждает сигнал 0 в пространстве вызывающего процесса;
недоступность данных живого процесса остаётся AccessDenied, а не доказательством
остановки. Сигналы направляются по локальному PID через kernel pidfd с повторной
проверкой поколения после открытия дескриптора. PID хостового пути не передаётся
в os.kill. Процесс namespace init завершает цепочку родителей.

Ожидание процесса не забирает статус дочернего процесса у Popen: адаптер Linux
читает waitid(WNOWAIT). Проверены совпадение числового PID чужого пространства,
устаревшая запись кэша, смена поколения перед сигналом, реальное завершение с
кодом 7, принадлежность дочернего интерпретатора launcher и обнаружение сирот QA.
Предыдущий пропуск независимой идентификации снят: проверка теперь выполняется
с реальным worker и проверкой ОС. Это не заменяет настоящий Windows Qt E2E.

## Общий риск и команда запуска

Изменение общего риска проходит через Supervisor и Coordinator. До медленного
опроса ОС читается версия реестра; во время опроса SQLite writer свободен,
поэтому STOP другого бота не ждёт обхода папок. Принятый RUNNING запрещает
публикацию лимитов даже до появления worker. После опроса берётся короткий
SQLite writer-барьер, повторно сравниваются ключи/состояния/command_version,
и только затем атомарно заменяется файл политики. START → STOP за время
проверки также меняет версию и запрещает публикацию. Этот барьер не меняет
контрольные ревизии, настройки ботов и PAPER Ledger. Уже существующие позиции
не закрываются. Во время атомарной публикации новая команда START ожидает
тот же SQLite writer; после выхода worker читает уже опубликованную политику.

До этого дополнения чистый полный прогон процессного слоя: 1359 PASS,
0 SKIP, fingerprint 48b236d9219bb9b2dd6921f7bf4cd83a15ebf55b0d62789ab67fd872cc3db959.
Для дополнения общего риска выполняется новый полный прогон; результаты
сохраняются в актуальном checkpoint, а не прибавляются к предыдущему числу.

## Проверка взаимосвязанных операций и восстановления

Предыдущий полный чистый прогон после общего риска: 1364 PASS, 0 SKIP,
fingerprint 076974070f14b316c4464a7281ec484eecadaa8922adfa9da5958fdd1feb7776.
Это исторический результат до следующих изменений, а не подтверждение их.

Импорт раньше освобождал исходный BotLock сразу после preflight. Теперь весь
набор местных исходников собирается заранее и удерживается до общей commit
или rollback. Supervisor сначала берёт уникальные полосы по индексу, затем
командные OS-gates по ключу. Это учитывает коллизии полос и встречный порядок
ботов в ZIP. Принятый START запрещает операторское изменение даже при ещё
не созданном worker. Регрессия проверяет второй независимый Supervisor,
публикацию/сбой, освобождение всех блокировок, повторяющиеся исходники,
встречные пакеты и неизменность исходных SQLite/config.

Денежный аудит раньше не выявлял изменение qty/average/fees при неизменном
cash. Новый position_journal получает реальные OPEN/DCA/PARTIAL/CLOSE,
FUNDING и SETTLE с идентификатором цикла. Независимый replay сверяет состояние,
денежные движения, остаточную комиссию, фиксированный leverage/margin_mode,
маржу и компенсацию PAPER Isolated, а также shares/cost/fee Polymarket.
Инкрементальная проверка внутри транзакции хранит только финансовые факты,
без повторного чтения полной истории или копирования сеток/таймлайнов.
Полный аудит читает все исполнения и состояние из одного SQLite snapshot,
в порядке rowid, не сортируя по корректируемому рыночному времени.

Неизменённые старые циклы без position_id остаются под прежним денежным
аудитом; миграция не подменяет недостающую историю искусственными сделками.
Новое открытие старого счёта уже получает полноценные receipts. Отдельно
проверяются DCA/частичный выход/funding обоих направлений для семи движков,
перенос и независимое закрытие, поздний funding закрытого цикла, три варианта
официального исхода Polymarket и отказ восстановления повреждённых данных.
Текущие результаты определяются новым полным прогоном и fingerprint checkpoint.

Замороженные финансовые настройки, план сетки, бюджет, правила количества и
данные исхода Polymarket привязаны к digest открытия. Проверяются также spent,
original_qty, funding_total, частичный realized и cycle_pnl архива. Funding-ID
новых циклов основан на position_id; одинаковые timestamps больше не перезаписывают
закрытые циклы. Старая схема funding-ID сохраняется для старых позиций.
Проверка компенсации Isolated учитывает реально действовавшую margin_model
исполнения: прежний PAPER-режим не подменяется новым публичным маржинальным
контрактом при аудите. Fixture Pump/Dump задаёт секцию до OPEN, вместо смены
принадлежности уже открытой позиции задним числом.

Реальные subprocess-проверки охватывают независимый соседний PAPER-счёт,

Проверки кода между этапами и после завершения связаны исходным SHA-256

synthetic JUnit fixture: негативный тест теперь изменяет реальный count,
а положительный сверяет его с независимым inventory.


## CP1251, сохранение отказов проверки и независимые котировки позиций

Отчёт BCC_VALIDATION_RESULTS_20261104_201409_693772.zip относится к исходникам
842cf689f1b235b71ab49050c2886833f48a04f0918a37ba32acace580a4a719. Полные
восемь shard XML содержат 1466 cases: 1456 PASS, пять FAIL и пять разрешённых
Windows-пропусков. Четыре отказа — чтение UTF-8 отчёта через CP1251; пятый —
искажённый статус при таком же чтении после фактического Qt/PAPER-сценария.
Следующие стадии health/manual этим запуском не подтверждены.

Все собственные Path.read_text/write_text явно задают кодировку. Дочерний
Python пишет перенаправленные stdout/stderr в UTF-8 без смены системной
кодировки и без принудительного PYTHONUTF8. Тестовый opt-in профиль CP1251
проверяет файловые и subprocess-границы; он не заменяет нативную Windows Qt.
Произвольные байты имени процесса в /proc сохраняются через surrogateescape.
Полные неуспешные shard XML теперь попадают в сводный JUnit с исходными
отказами; неполный inventory по-прежнему блокируется. Наличие XML не даёт PASS.

Котировки открытых позиций ранее ожидали свечи/funding в том же future.
Для источников с position_orderbook введена отдельная ограниченная очередь:
свежий реальный стакан передаётся владельцу счёта независимо от загрузки
индикаторной истории. История и финансовый учёт остаются на прежних путях;
пороги свежести не расширены. Регрессия блокирует свечи и проверяет доставку
котировок нескольких позиций и фактический защитный PAPER CLOSE с аудитом
журнала до разблокирования истории. Устаревшие стаканы не исполняются.

Это подтверждённый дефект кода, но не доказательство единственной причины
ошибок на пользовательском скриншоте. Для текущего рабочего окна требуется
BCC_CURRENT_REPORT из «Сохранить отчёт»; остановка счетов для него не нужна.
Готовность релиза и нативная приёмка изменённого кода остаются неподтверждёнными.
